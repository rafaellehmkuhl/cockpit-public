The data lake

One bus. Everything on it. Every door leads here.

The bus

Every value in Cockpit lives in one place

A flat, observable key–value store. Telemetry, internal state, your data — no distinction.

Instead of writing display code, you put a number in the lake and bind a widget to it.

Addressing

Variable ids are just strings

SourceId format
MAVLink fieldmavlink/{sys}/{comp}/ATTITUDE/roll
Named valuemavlink/{sys}/{comp}/NAMED_VALUE_FLOAT/{name}
Another vehicle (mirrored)mavlink/{its sys}/{comp}/GLOBAL_POSITION_INT/lat
Generic WebSocketexternal/{key}/{nested-key}
USB GNSSexternal/positioning/gnss/{device}/{field}
Point of interestcockpit/pois/{id}/latitude
Joystick axisinputs/mavlink/axis-x

There is no enforced namespace. To expose a new MAVLink field, extend the flattener in src/libs/vehicle/common/data-flattener.ts — never special-case a widget.

Reading the lake

{{ id }} reads any value, anywhere

{{ external/watertemp }}                                      → 18.4

{{ mavlink/1/1/GLOBAL_POSITION_INT/relative_alt }}            → 12500 (mm)
{{ mavlink/1/1/GLOBAL_POSITION_INT/relative_alt : metric }}   → 12.5  (m)
{{ mavlink/1/1/GLOBAL_POSITION_INT/relative_alt : imperial }} → 41.0  (ft)

The suffix is metric, imperial or nautical. Leave it off and you get the value as stored.

Works in HTTP actions (URL, query, headers, body), MAVLink message fields, compound variables, WebSocket URLs, indicator text and the video telemetry overlay.

Derived values

Compound variables: JavaScript over the lake

compound variable · pressure-limit-reached
// true while the payload is past its rated depth
{{ external/pressure }} > 250000

The result is a real data-lake variable, a boolean here, updated with every new pressure reading: plottable, recordable, and ready to fire an action.

Any variable you create can also persist across reboots: the definition, the last value, or both.

The WebSocket door

Zero code inside Cockpit. One short script outside it.

Door 1 · the protocol

The entire wire format

one message, over the WebSocket
{
  "WaterTemp": 18.4,
  "Sonar": {
    "Ping": { "Distance": 12.3 }
  },
  "Winch": { "Locked": false },
  "PayloadStatus": "Logging"
}
what lands in the data lake
IdValueType
external/watertemp18.4number
external/sonar/ping/distance12.3number
external/winch/lockedfalseboolean
external/payloadstatusLoggingstring

Every key is a variable, nesting becomes the path, and the JSON value sets the type. Plain text also works: WaterTemp=18.4. An object whose type starts with cockpit: is a command instead.

Door 1 · the other side

The entire server

feed.py
import asyncio, json, random, websockets

async def handler(ws):
    while True:
        reading = {"WaterTemp": round(20 + random.random(), 2)}
        await ws.send(json.dumps(reading))
        await asyncio.sleep(1)

async def main():
    async with websockets.serve(handler, "0.0.0.0", 8765):
        await asyncio.Future()

asyncio.run(main())

Then, in Cockpit

Settings → General → Generic WebSocket connections → paste ws://localhost:8765

The URL accepts data-lake variables, so ws://{{ vehicle-address }}:8765 follows the vehicle you're connected to.

Auto-reconnects every 2 s. Survives restarts on both ends.

Live demo

One script, on stage

1 Run feed.py, visible on screen
2 Paste ws://localhost:8765 into Cockpit
3 Data lake → filter external → values ticking
4 Drop a Plotter on it. Done.
If it fails: no debugging on stage. Ten seconds, then move on.

Door 2 · composing

Any action can read the lake

cockpit-http-request-actions · one stored action
{
  "name": "Report to the winch",
  "method": "POST",
  "url": "http://{{ vehicle-address }}:9000/telemetry",
  "headers": {
    "Content-Type": "application/json",
    "Authorization": "Bearer {{ winch-api-token }}"
  },
  "urlParams": {
    "vehicle": "{{ autopilotSystemId }}"
  },
  "body": {
    "source": "cockpit",
    "temp_c": {{ external/watertemp }},
    "depth": {{ mavlink/1/1/VFR_HUD/alt }}
  }
}

Everywhere: URL, query parameters, headers and body. The same {{ }} works in MAVLink message fields.

MAVLink message action

Compose any MAVLink message, fill fields from the lake, send it. The autopilot needs nothing Cockpit-specific.

Door 3 · new in v1.19

Or let an agent write it

Cockpit Standalone runs a local MCP server. Point any MCP client at it and the agent gets the same doors you do — as tools.

a few of the 34 tools
list_data_lake_variables   save_transforming_function
save_http_request_action   execute_action
add_view                   add_widget
add_diy_widget             add_point_of_interest
evaluate_expression        take_screenshot

Off by default

  • Localhost only, bearer token
  • Creating or running code is a second opt-in
  • Standalone only — the browser can't host a server

"Build me a view for my sonar payload" is now a sentence, not an afternoon.

Recap

Pick the lowest door that works

DoorUse it when
1 · WebSocketYou have values and want them seen, plotted, logged
2 · ActionsYou need Cockpit to call you, or the vehicle to react
3 · DIY widgetYou need a custom display and don't want to host anything
4 · iframeYou already have a web UI worth keeping
+ · MCPYou'd rather describe it than build it

Most people reach for door 4 when door 1 would have done. Don't.
