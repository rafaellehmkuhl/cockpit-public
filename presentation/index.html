00

The data lake

One bus. Everything on it. Every door leads here.

The bus

Every value in Cockpit lives in one place

A flat, observable key–value store. Telemetry, internal state, your data — no distinction.

Once a value is in there, every consumer already works: plotters, indicators, gauges, telemetry overlays, CSV logs, joystick bindings, action triggers.

You do not write display code. You put a number in the lake and bind a widget to it.

Fed by

  • MAVLink messages (auto-flattened)
  • Generic WebSocket connections
  • Joystick axes and buttons
  • USB / serial GNSS receivers
  • Points of interest on the map
  • Your JavaScript, via window.cockpit
  • Other data-lake variables, transformed

530 variables — with nothing connected

Addressing

Variable ids are just strings

SourceId format
MAVLink field/mavlink/{sys}/{comp}/ATTITUDE/roll
Named value/mavlink/{sys}/{comp}/NAMED_VALUE_FLOAT/{name}
Generic WebSocketexternal/{machinized-name}
USB GNSSexternal/positioning/gnss/{device}/{field}
Point of interestcockpit/pois/{id}/latitude
Joystick axisinputs/mavlink/axis-x
Built-invehicle-address

There is no enforced namespace. To expose a new MAVLink field, extend the flattener in src/libs/vehicle/common/data-flattener.ts — never special-case a widget.

Derived values

Compound variables: JavaScript over the lake

expression
// depth from pressure, live
({{ external/pressure }} - 101325)
  / (1025 * 9.80665)

The result becomes a real data-lake variable — plottable, recordable, bindable to a joystick, usable as an action trigger.

Also persistent

User-created variables can survive reboots — the definition, the value, or both.

persistent keeps the variable; persistValue keeps its last value.

01

The WebSocket door

Zero code inside Cockpit. Four lines outside it.

Door 1 · the protocol

The entire wire format

variableName=value
  • One variable per message. Not JSON. Not batched.
  • Type is guessed once, from the first value, then locked forever.
  • Quote it to force a string: Status="12"
  • Lands at external/ + a machinized name.

WaterTemp=23.5  →  external/watertemp, typed number.

Door 1 · the other side

The entire server

feed.py
import asyncio, websockets

async def handler(ws):
    while True:
        await ws.send("WaterTemp=23.5")
        await asyncio.sleep(1)

async def main():
    async with websockets.serve(handler, "0.0.0.0", 8765):
        await asyncio.Future()

asyncio.run(main())

Then, in Cockpit

Settings → General → Generic WebSocket connections → paste ws://localhost:8765

The URL accepts data-lake variables, so ws://{{ vehicle-address }}:8765 follows the vehicle you're connected to.

Auto-reconnects every 2 s. Survives restarts on both ends.

One field. One button.

Start to finish, no code in Cockpit

Arrived: typed, live, and yours

Live demo

Four lines, on stage

1 Run feed.py — 4 lines, visible on screen
2 Paste ws://localhost:8765 into Cockpit
3 Data lake → filter external → values ticking
4 Drop a Plotter on it. Done.

02

Actions

Getting data in is half of it. Now make something happen.

Three kinds of action. That's all of them.

Door 2 · composing

Any action can read the lake

HTTP request action · body
{
  "vehicle": "{{ vehicle-address }}",
  "temp_c":  {{ external/watertemp }},
  "alt_m":   {{ external/sonaraltitude }},
  "depth":   {{ /mavlink/1/1/VFR_HUD/alt }}
}

Same {{ }} syntax in the URL, in query parameters, and in MAVLink message fields.

Gotcha: the URL, query params and body are interpolated. Headers are not. If you need a dynamic token in a header today, you need a JavaScript action.

MAVLink message action

Compose any MAVLink message, fill fields from the lake, send it. No firmware knowledge of Cockpit required.

Door 2 · firing

Four ways to pull the trigger

  • A joystick button Any button, with a shift modifier
  • An on-screen element Button, switch, slider, dial, dropdown
  • A data-lake change — action links Fires when a variable moves, rate-limited by minInterval
  • Time — auto-run Once at startup, or on an interval

Worked example. external/watertemp crosses a threshold → a compound variable goes true → an action link fires an HTTP request to your service → your winch pays out. Nothing compiled, nothing forked, and it survives a Cockpit update.

First-party actions use the same mechanism

03

The DIY widget

When you need pixels, not just values.

Door 3

Write a widget without leaving the app

DIY widget · js
const el = document.getElementById('temp')

window.cockpit.listenDataLakeVariable(
  'external/watertemp',
  (v) => { el.textContent = v.toFixed(1) + ' °C' }
)

Three panes — HTML, CSS, JS — in a Monaco editor, with autocomplete over variable ids and live values in the hover tooltips.

Inherits the interface

One toggle and your widget picks up Cockpit's glass styling, so it doesn't look bolted on.

Not sandboxed. Your JavaScript is appended to Cockpit's own document and runs with the same privileges as the app. Powerful, and a real trade-off — treat shared DIY widgets like you'd treat any script you paste into a console.

Same palette as every built-in widget

04

iframe + CockpitAPI

You already have a web app. Bring it.

Door 4

Your existing UI, as a widget

in your page
CockpitAPI.listenToDatalakeVariable(
  'external/watertemp',
  (value) => render(value),
  10 // max Hz
)

Ships as a browser bundle: yarn build:lib → cockpit-external-api.browser.js

under the hood · postMessage
// child → Cockpit
{ type: 'cockpit:listenToDatalakeVariables',
  variable: 'external/watertemp', maxRateHz: 10 }

// Cockpit → child
{ type: 'cockpit:datalakeVariable',
  variable: 'external/watertemp', value: 23.5 }

Honest limitation: the bridge is listen-only. A child page can read telemetry but has no documented way to write back into the lake. If you need to write, use door 1 or door 3.

Door 4 · options worth knowing

Small things that save you hours

  • useVehicleAddressAsBase — your URL resolves against the connected vehicle No hardcoded IPs, and it follows the operator when they switch vehicles
  • contentZoom and scaleContentWithWidget Your page stays legible when the operator resizes the widget
  • collapsibleContainerName and startCollapsed Dock the widget into a collapsible drawer instead of eating canvas
05

The extension manifest

Ship the whole experience, not just a page.

Door 5 · discovery

How Cockpit finds you

GET /helper/v1.0/web_services
→
metadata.extras.cockpit
→
fetch that path
→
ExtrasJson

Cockpit asks BlueOS what services are running. Any service that declares extras.cockpit in its metadata gets fetched at whatever relative path it names.

There is no fixed endpoint like /cockpit-widgets. You choose the path; Cockpit follows it.

Door 5 · the contract

One file, three arrays

{
  "targetSystem": "cockpit",
  "targetCockpitApiVersion": "1.0.0",

  "widgets": [
    { "name": "Sonar Payload",
      "iframeUrl": "/ui/panel.html",
      "iconUrl": "/ui/icon.svg",
      "useExtensionPathAsBaseUrl": true,
      "collapsibleContainerName": "Payload" }
  ],

  "actions": [
    { "id": "payload-ping", "name": "Ping payload", "type": "http-request",
      "config": { "url": "http://{{ vehicle-address }}:9000/ping", "method": "POST" } }
  ],

  "joystickSuggestions": [ /* ... */ ]
}
Door 5 · the one nobody expects

Your extension can propose button mappings

{
  "id": "sonar-payload-map",
  "name": "Sonar payload controls",
  "targetVehicleTypes": ["sub", "rover"],
  "buttonMappingSuggestions": [
    { "actionProtocol": "cockpit-action",
      "actionId": "payload-ping",
      "actionName": "Ping payload",
      "button": 3,
      "modifierKey": "shift" }
  ]
}

Ship a payload, and ship the controls for it — so the operator doesn't have to read your manual to find out that shift+Y pings the sonar.

It's a suggestion. The operator sees a review dialog and accepts or ignores it. You cannot silently rebind someone's controller.

Keys may be snake_case — the schema normalises them.

Door 5 · the rule that makes it safe

Nothing applies itself

Every suggested widget, action and mapping goes through a review dialog. The operator accepts, ignores, or restores it later.

This is why an operator can install your extension the morning of a dive without reading the source.

Which also means

  • Your integration is discoverable, not imposed
  • Uninstalling your extension doesn't wreck their layout
  • An operator can run three payload extensions at once

06

Rough edges

The things I'd rather you heard from me than found at 2am.

Known, current, in v1.19

What's still wrong

  • WebSocket ingestion is plain text, one variable per message No JSON. Type locks on the first value it ever sees.
  • DIY widget JavaScript is not sandboxed It runs in Cockpit's own page, with Cockpit's privileges
  • The iframe bridge is listen-only No documented write path from the child page
  • HTTP action headers aren't interpolated Only URL, query params and body
  • targetCockpitApiVersion isn't enforced It's parsed, then nothing gates on it
  • The manifest schema isn't documented The Zod types in the repo are the only spec — this slide is closer to docs than anything we ship

Every one of these is small, well-scoped, and genuinely useful. If you want a way in, this is the list.

The honest bit

I'm the wrong person to test your copter

Blue Robotics builds submarines and boats. We test ArduSub and ArduRover every single day, against real hardware.

Straight from our own README: aerial support is initial. ArduCopter has been physically tested, but the core team doesn't fly regularly — "use it at your own risk."

That is not false modesty. It's a gap, and it's the gap that matters most to this room.

What I'm asking for

  • Copter and plane testers
  • Someone to own aerial defaults Widgets, joystick profiles, mission behaviour
  • Bug reports from vehicles I'll never own

PRs from outside this team already shipped TCP/UDP, bitfields and the EKF widget. It works.

Before

After · v1.18

Every write carries a timestamp. Newest wins. Automatic, scoped per user and per vehicle. No modal.
